# v0.1 Vertical Slice — User Stories

> The first thing users can do end-to-end. Single workspace, English only,
> one container, SQLite. This is the slice that proves the model — everything
> else (multi-user, PWA, push, cadences) builds on top.

**Slice goal:** a self-hosted operator can `docker compose up`, complete the
setup wizard, log in, create a contact, log an interaction, and see it on the
contact's timeline.

---

## E1 — Setup wizard

| # | Story | Acceptance |
|---|-------|-----------|
| **E1.1** | As a self-hoster on a fresh instance, I see a setup wizard on first visit. | `GET /` redirects to `/setup` when no users exist. |
| **E1.2** | I create the first admin account (email + password + display name). | `POST /api/setup` creates a `User` with `IsInstanceAdmin = true` and a default personal `Workspace` where the user is `Owner`. Returns 200 + a session cookie. |
| **E1.3** | The instance refuses to run the wizard twice. | `POST /api/setup` returns `409 setup_already_complete` if `Instance.SetupCompletedAt` is non-null. |
| **E1.4** | Password validation runs before commit. | Passwords shorter than 12 chars or matching the email local-part are rejected with `400 weak_password`. |

## E2 — Authentication

| # | Story | Acceptance |
|---|-------|-----------|
| **E2.1** | As a registered user, I can sign in with email + password. | `POST /api/auth/login` returns `200` + `access_token` (JWT, 15 min) + `refresh_token` (httpOnly cookie, 30 days) on success. |
| **E2.2** | I get a clear error on bad credentials. | `POST /api/auth/login` returns `401 invalid_credentials` with no body details. (Constant-time; same message for "user not found" vs "wrong password".) |
| **E2.3** | I can refresh my access token using the refresh cookie. | `POST /api/auth/refresh` returns a new `access_token` + rotated `refresh_token`. Old refresh token is invalidated. |
| **E2.4** | I can sign out, which revokes the current session. | `POST /api/auth/logout` invalidates the `refresh_token`, clears the cookie, returns `204`. |
| **E2.5** | Rate limiting slows brute-force attempts. | `/api/auth/login` is rate-limited at 10 attempts/min per IP; over-limit returns `429 too_many_requests`. |
| **E2.6** | Passwords are stored as Argon2id, never plaintext. | Inspect the `users` table after registration — `PasswordHash` matches `$argon2id$v=19$m=…$…$…`. |

## E3 — Workspace switching

| # | Story | Acceptance |
|---|-------|-----------|
| **E3.1** | After login I land on the personal workspace. | The dashboard shows my personal workspace by default; the workspace selector in the top bar lists all workspaces I'm a member of. |
| **E3.2** | I can switch to another workspace I belong to. | Switching changes the active workspace id; subsequent API calls include the new id and return only that workspace's data. |
| **E3.3** | I cannot access a workspace I don't belong to. | Any `/api/workspaces/{id}/...` call from a non-member returns `403 forbidden`. |

## E4 — Contacts CRUD

| # | Story | Acceptance |
|---|-------|-----------|
| **E4.1** | I can see a paginated list of contacts in my active workspace. | `GET /api/workspaces/{id}/contacts?limit=50&offset=0` returns ≤ 200 rows ordered by `LastName, FirstName`. |
| **E4.2** | I can create a contact with required + optional fields. | `POST /api/workspaces/{id}/contacts` with `{firstName, lastName, …}` returns `201` + `Location: /api/workspaces/{id}/contacts/{newId}`. |
| **E4.3** | I can view a single contact's profile. | `GET /api/workspaces/{id}/contacts/{contactId}` returns the full `ContactDto`. |
| **E4.4** | I can update a contact with optimistic concurrency. | `PATCH …/{contactId}` requires the client's last-known `version`; mismatched versions return `409 stale_version`. |
| **E4.5** | I can soft-delete a contact and restore it within 30 days. | `DELETE …/{contactId}` sets `DeletedAt`; the row remains in the DB and can be restored via the trash view (v0.3+). |
| **E4.6** | I can search contacts by name. | `GET …/contacts?q=ada` returns contacts whose full name contains "ada" (case-insensitive, accent-stripped). |
| **E4.7** | Soft-deleted contacts are excluded from the list by default. | `GET …/contacts?includeDeleted=true` is opt-in. |

## E5 — Interactions (timeline)

| # | Story | Acceptance |
|---|-------|-----------|
| **E5.1** | I can log a new interaction with one or more contacts. | `POST /api/workspaces/{id}/interactions` with `{kind, direction, occurredAt, participantContactIds[]}` returns `201`. |
| **E5.2** | The contact's timeline shows interactions in reverse chronological order. | `GET /api/workspaces/{id}/contacts/{contactId}/interactions` returns up to 100 most recent, newest first. |
| **E5.3** | I can attach a note to an interaction (Markdown). | `POST …/interactions` with `notes` saves the Markdown text; rendered HTML is sanitised on the client. |
| **E5.4** | Logging an interaction offline queues it and syncs when online. | Network-tab shows POST after reconnection; duplicates are deduped via the `clientGeneratedId` idempotency key (v0.2 dependency). |
| **E5.5** | The contact's profile shows a "last contacted" date. | Computed from the most recent non-deleted `Interaction` for that contact. |

## E6 — Reminders (basic)

| # | Story | Acceptance |
|---|-------|-----------|
| **E6.1** | I can create a one-off reminder for any date. | `POST /api/workspaces/{id}/reminders` with `{title, dueAt}` returns `201`. |
| **E6.2** | I can see upcoming and overdue reminders on the dashboard. | `GET /api/workspaces/{id}/reminders?upcoming=true&overdue=true` returns the relevant subset, ordered by `dueAt`. |
| **E6.3** | I can mark a reminder as done or dismiss it. | `PATCH …/reminders/{id}` with `{status: 'completed' \| 'dismissed'}` updates it. |
| **E6.4** | Birthday reminders are created automatically. | A Hangfire job runs at signup time and daily to populate `Reminder`s for contacts with `birthday` set; `GET …/reminders?kind=birthday` returns them. |

## E7 — Observability baseline

| # | Story | Acceptance |
|---|-------|-----------|
| **E7.1** | The instance exposes a liveness probe. | `GET /healthz` returns `200 OK`. |
| **E7.2** | The instance exposes a readiness probe that checks dependencies. | `GET /readyz` returns `200` only when DB + storage + (configured) SMTP respond. |
| **E7.3** | Every API call is logged as structured JSON in production. | `Serilog` emits one line per request including `TraceId`, `UserId`, `WorkspaceId`, status, duration. |
| **E7.4** | Every mutation produces an `AuditLog` entry. | `POST /contacts` adds an `audit_logs` row with `Action=Create`, `EntityType="Contact"`. |

## E8 — Operational baseline

| # | Story | Acceptance |
|---|-------|-----------|
| **E8.1** | The container is non-root. | `docker exec personal-crm whoami` returns `personalcrm`. |
| **E8.2** | The DB lives on a mounted volume, not inside the image. | `docker inspect` shows a bind/volume mount on `/app/data`. |
| **E8.3** | Attachments live under the same data directory. | `ls ./data/attachments` shows uploaded files; the row in `attachments` references the relative key. |
| **E8.4** | A first-run Hangfire job creates the daily backup schedule. | `GET /hangfire/recurring` shows the `DatabaseBackup` job. |
| **E8.5** | Updating the image runs the new migrations automatically. | `docker compose up --build` against a v0.0.5 DB applies v0.1 migrations before the app starts serving. |

## Definition of Done — v0.1

A user can:

1. Run `docker compose up -d` and reach `http://localhost:8080`.
2. Complete the setup wizard (admin account).
3. Sign in.
4. Create a contact.
5. Log an interaction with that contact.
6. Open the contact and see the interaction in the timeline.
7. Set a reminder and see it on the dashboard.

…with:

- All `dotnet test` green on CI.
- `docker compose down && docker compose up` preserving all data.
- No `P0` bugs open against the slice.
- `ROADMAP.md` updated to mark v0.1 ✅.
